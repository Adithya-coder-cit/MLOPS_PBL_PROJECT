## 1. Problem Statement

Public transport riders choose routes without visibility into the risk of
disruption (delays, cancellations, weather-driven service degradation).
RouteWise aims to combine disruption-risk prediction with multi-objective,
multi-modal route optimization so recommendations account for cost, travel
time, and reliability together, and adapt when disruption risk changes.

## 2. Objectives

1. Predict the probability of transport disruption from weather, historical
   delay, and temporal features.
2. Represent the transport network as a weighted graph and generate
   multi-modal candidate routes.
3. Score and rank routes using `Score = αC + βT − γR` (cost, time,
   reliability), with reliability weighted more heavily as predicted
   disruption risk rises.
4. Support adaptive rerouting when disruption risk changes.
5. Implement a full MLOps lifecycle: versioned data, tracked experiments, a
   model registry with promotion gates, monitoring, drift detection, and
   retraining triggers.

## 3. Architecture

Seven layers, per the project specification:

1. **Data Sources** — GTFS, weather data, historical delay data
   (development mode: synthetic demo dataset; production mode: real feeds)
2. **Data Ingestion & Storage** — validation, deduplication, versioning
3. **Processing & Feature Engineering** — cleaning, normalization, temporal
   alignment, feature generation
4. **Predictive Intelligence** — XGBoost (primary), Random Forest (baseline)
5. **Constraint-Aware Decision Engine** — `Score = αC + βT − γR` with
   adaptive reliability weighting
6. **Graph-Based Routing** — NetworkX, Dijkstra, A*
7. **Presentation Layer** — FastAPI backend + React/TypeScript dashboard

MLOps lifecycle: Data Ingestion → Validation → Processing → Feature
Engineering → Model Training → Experiment Tracking (MLflow) → Model
Evaluation → Model Registry → Model Serving → Monitoring (Evidently) →
Drift Detection → Retraining Trigger → back to Model Training. Data and
pipeline stages are versioned with DVC.

**Implementation status of each layer:** see section 17 (Limitations).

### Data Validation, Preprocessing & Feature Engineering

**Implemented.** `python -m src.features.build_dataset` runs the full
Raw → Validation → Preprocessing → Feature Engineering → Temporal Split
pipeline:

- **Validation** (`src/validation/`): schema, dtypes, nulls, duplicates,
  PK/FK integrity, categorical/numeric ranges, timestamp validity,
  disruption-label consistency, DEMO-metadata banner. Fails loudly
  (`ValidationError`) on any ERROR-level issue — never silently repairs
  data. Machine-readable reports: `data/interim/raw_validation_report.json`,
  `data/processed/feature_validation_report.json`.
- **Preprocessing** (`src/preprocessing/`): datetime parsing, sorting,
  duplicate handling, a backward-only asof-join to weather (bounded
  tolerance — never a future reading), route/mode joins. A separate
  sklearn `ColumnTransformer` (median-impute + scale numeric, one-hot
  categorical) is fit **only on the train split** and persisted to
  `data/processed/preprocessor.joblib`.
- **Feature engineering** (`src/features/`): weather, temporal
  (hour/day-of-week/peak-off_peak-night/time-of-day bucket),
  `transfer_dependency` (recomputed from the static schedule),
  and leakage-safe historical features (`historical_delay_minutes`,
  `rolling_7d_delay_minutes`, `historical_reliability`) computed via a
  strict `groupby(route).shift(1).expanding()/.rolling()` — a day's value
  never includes that day's own outcome.
- **Temporal split**: chronological, boundaries computed from the actual
  observed date range (not hardcoded), no overlap between splits.
- **Feature manifest**: `data/processed/feature_manifest.json` — every
  column's dtype, source, transformation, availability time, leakage
  risk, and model usage (feature / label / identifier / excluded).
- **Dataset metadata**: `data/processed/dataset_metadata.json` — DVC
  content hashes of the raw data used, generation seed, config hash,
  row counts, schema versions, split boundaries.

Anti-leakage guarantees are proven by dedicated tests, not just asserted
— see `tests/test_feature_leakage.py`.

## 8. Training

**Implemented.** `python -m training.train` trains XGBoost (primary) and
Random Forest (baseline) against the Stage 3 processed dataset — read-only,
never regenerates or modifies it. Verifies schema/target/temporal ordering
before training (fails loudly otherwise). Missing values: XGBoost uses
native NaN handling (`enable_categorical=True`, no imputation); Random
Forest uses the Stage 3 `preprocessor.joblib` (train-fit only). Class
imbalance (train ratio 2.74:1) triggers `scale_pos_weight` /
`class_weight="balanced"`, decided from train data only — no oversampling.
A modest, curated hyperparameter search (5 configs each, see
`params.yaml` `model.*.search_grid`) is scored on validation only; the
test set is evaluated exactly once, after model selection. Real results
in section 16 below — see `models/evaluation/evaluation.json` for full
detail (validation vs. test kept explicitly separate).

### Promotion gate

`params.yaml` `evaluation.promotion_gates` — explicitly documented as
**engineering acceptance criteria, not scientifically derived
thresholds**. A candidate must clear absolute minimums (PR-AUC, recall,
precision, F1, ROC-AUC) and, if a production model already exists, not
regress beyond a configurable tolerance vs. it. Real result on the
current candidates: **gate did not pass** — F1 (~0.50–0.51) is below the
configured `min_f1: 0.60`, even though PR-AUC/recall/precision/ROC-AUC
all cleared their minimums. Both models therefore remain at
`lifecycle_stage=Candidate`, not `Validated`, and neither is promotable
(`training/promote_model.py` explicitly refuses to promote anything that
isn't `Validated`, and separately refuses without `--confirm`) — verified
by actually attempting it. This is the gate legitimately gating, not a
rubber stamp.

### Model loading (`inference/model_loader.py`)

Never hardcodes a filename — always resolves through the registry, by
the `production` alias or an explicit version. Since no model is
promoted yet, `load_production_model()` correctly raises
`NoProductionModelError` (verified). A genuine MLflow/XGBoost interop
gap was found and fixed here: `mlflow.xgboost.load_model()` drops the
sklearn wrapper's `n_classes_` attribute on reload, and MLflow's generic
pyfunc schema enforcement can't round-trip pandas `category`-dtype
columns through JSON — so this module loads each model via its native
flavor and repairs `n_classes_` for XGBoost. Verified byte-identical
`predict_proba` output vs. the pre-registration model.

### Graph Routing + Constraint-Aware Decision Engine

**Implemented.** `src/routing/` builds a NetworkX `DiGraph` directly from
the Stage 2/3 development dataset (never a hardcoded/synthetic graph) —
70 stop nodes, ~228 directed edges (one per (route_id, direction_id) leg,
using a representative trip per direction since the generator's schedule
template is identical across all departures of that leg). Every edge is
traceable: `src/routing/lineage.py` records, per value, the exact source
dataset/record and whether it's directly sourced or derived (e.g.
`travel_time` from `stop_times.csv` scheduled times — not derived; `cost`
apportioned from a route-level `fares.csv` fare — derived; disruption
probability from the trained model — derived).

- **Reliability**: `reliability = 1 - disruption_probability` per edge
  (the only definition used anywhere in the project); a route's
  reliability is the PRODUCT of its edges' reliabilities (independence
  assumption, documented) — `src/decision_engine/reliability.py`.
- **Normalization**: configurable — `minmax_candidates` (adaptive, across
  the candidate set for a query) or `fixed_bounds` (from `params.yaml`,
  used automatically for a single candidate) —
  `src/decision_engine/normalization.py`.
- **Score**: `Score = αC + βT − γR` over normalized values, lower is
  better; sign convention verified by a direct monotonicity test
  (`tests/test_decision_engine.py::test_score_sign_convention_monotonicity`)
  — `src/decision_engine/scoring.py`.
- **Adaptive weighting**: a deterministic policy switch — when a
  candidate's own disruption risk exceeds `high_risk_threshold`, its
  score uses `high_risk_weights` (reliability weighted more) instead of
  `baseline_weights`. Explicitly a configured decision policy, not a
  scientifically derived function — `src/decision_engine/adaptive_weighting.py`.
- **Candidate generation**: multiple strategies per query — shortest-time,
  lowest-cost, lowest-risk (each via Dijkstra) plus k-shortest-time paths
  — de-duplicated, then all scored and ranked (never a single
  shortest-path call) — `src/routing/candidates.py`.
- **Dijkstra**: configurable scalar weight — time / cost / risk (via a
  `-log(reliability)` transform so summing weights corresponds to
  multiplying reliabilities) / combined — `src/routing/path_search.py`.
- **A***: a genuine admissible heuristic (haversine distance ÷ max
  observed speed) for the `time` objective; for cost/risk/combined, no
  admissible non-trivial heuristic exists without fabricating one, so
  A* runs with heuristic=0 (still admissible, degenerates to Dijkstra) —
  documented, not hidden.
- **Transfers**: detected at path-aggregation time (a route_id change
  between consecutive legs), penalized exactly once per transfer point
  (time/cost/reliability) — never baked into search weights and never
  double-counted — `src/routing/path_aggregation.py`.
- **Adaptive rerouting**: `src/routing/rerouting.py`'s `reroute()` —
  explicitly an "adaptive rerouting capability," not real-time (no live
  feed connected). Demonstrated end-to-end in
  `tests/test_routing_engine.py::test_section18_controlled_disruption_scenario`.
- **Explanations**: generated from each route's actual computed values
  (never hardcoded text) — `src/decision_engine/explanation.py`.
- **Model availability**: no model is in Production yet (Stage 5's real
  finding). The routing engine never silently substitutes a candidate for
  a production model — `src/routing/prediction_source.py` requires an
  explicit `kind="production"` or `kind="candidate"` choice, and every
  `RouteResult` exposes `model_lifecycle_stage`, `is_production_model`,
  and (when non-production) a `model_source_warning`. The demonstration
  scenario explicitly uses the validated Candidate XGBoost model
  (registry version 4).

`/recommend-route`, and `/reroute` return `503 model_unavailable` with a
clear message — verified via dependency-override tests, not just
asserted.

network — not a production throughput claim): `/predict-disruption`
~15.6ms mean, `/recommend-route` ~7.0ms mean, over 20 warmed-up calls.

## 13. Monitoring

**Implemented** (`src/monitoring/`, Evidently AI 0.4.40 — the exact
version pinned in `requirements.txt`; its installed API was inspected
directly rather than assumed from another version's docs). Four
observational categories, all DEVELOPMENT/DEMO — this project has no
production model or live traffic:

- **Data quality** — missing values (Evidently `DatasetMissingValuesMetric`),
  schema changes, new/unseen categorical values, values outside the
  reference-observed range, and duplicate records, against
  `data/processed/feature_manifest.json`'s own feature list.
- **Data (feature) drift** — reference (`train.parquet`) vs. current
  (`test.parquet`) distribution of every model feature, via Evidently's
  `ColumnDriftMetric`/`DatasetDriftMetric`: Kolmogorov-Smirnov for numeric
  columns, Population Stability Index for categorical columns, both with
  documented, configurable thresholds (`params.yaml` `monitoring.data_drift`).
- **Prediction drift** — the model's own predicted-probability and
  predicted-class distributions, reference vs. current, using the same two
  methods — deliberately reported and decided on separately from feature
  drift (drift in one does not imply drift in the other).
- **Performance monitoring** — reuses `training/evaluate.py`'s exact
  precision/recall/F1/ROC-AUC/PR-AUC definitions against the current
  batch's real labels, compared to the model's own recorded training-time
  test metrics. Explicitly reports
  `"Performance evaluation unavailable because ground-truth labels are not
  yet available."` rather than fabricating a metric when labels are absent.

A deterministic, config-driven decision policy (`src/monitoring/decision.py`)
turns these into one signal — `NO_ACTION` / `REVIEW_REQUIRED` /
`RETRAINING_RECOMMENDED` — for Stage 10 to consume later; **Stage 9 never
retrains anything**, and feature/prediction drift alone can only ever reach
`REVIEW_REQUIRED`, never `RETRAINING_RECOMMENDED` (drift is not equated
with model failure — only a measured performance regression escalates that
far). Local/development operational counters (request count, success/
failure, prediction/route-recommendation errors, latency) are tracked live
by `api/middleware.py` and exposed alongside the monitoring result.

Run a monitoring pass:

```bash
python -m src.monitoring.runner
```

Reference dataset lineage (dataset version, DVC content hash,
feature-manifest version, model name/version, git SHA) is captured once
into `data/interim/monitoring/reference_metadata.json` and never silently
changed — a later run whose lineage no longer matches raises
`ReferenceChangedError` unless `--force-reference` is passed. Each run
writes a machine-readable `data/interim/monitoring/latest_monitoring_report.json`
(committed, like the other small pipeline reports) and Evidently HTML
reports under `data/interim/monitoring/html_reports/` (gitignored,
regenerated per run, not committed). `GET /system/status` exposes the last
run's result (`NOT_RUN` in every category if no run has ever completed —
never a fabricated "healthy") plus the live operational snapshot; the
dashboard's MLOps panel shows the same real per-category statuses. Four
deterministic controlled scenarios (identical data, a seeded feature
shift, a seeded prediction shift, and seeded performance degradation) are
exercised as real tests in `tests/test_monitoring.py` — see section 15.

## 16. Model Performance

Real results from the trained candidates against the held-out **test**
split (evaluated once, after model selection on validation). Decision
threshold 0.5. Full detail — including validation-stage numbers, confusion
matrices, threshold sensitivity, calibration, and reproducibility metadata
— in `models/evaluation/evaluation.json`.

| Model | Precision | Recall | F1 | ROC-AUC | PR-AUC | Training time |
|---|---|---|---|---|---|---|
| Random Forest (tuned) | 0.427 | 0.610 | 0.502 | 0.707 | 0.516 | 204.5s |
| XGBoost (tuned) | 0.423 | 0.633 | 0.507 | 0.710 | 0.520 | 4.3s |

**Trade-offs, not a single "winner":** XGBoost has a marginal edge on
every ranking/threshold metric (F1, ROC-AUC, PR-AUC, recall) and trains
~48x faster — a large practical advantage for iteration and retraining.
Random Forest has slightly higher precision (fewer false alarms per
flagged disruption). Both are well above the ~0.267 positive-class base
rate (a PR-AUC of ~0.27 would indicate no signal), but neither is
strongly discriminative yet (ROC-AUC ~0.71) — expected at this stage:
the synthetic data was deliberately generated with a non-trivial noise
component (see `configs/synthetic_data.yaml` `disruption_noise`) rather
than a near-deterministic label, precisely so training wouldn't produce
artificially perfect metrics.

**Feature importance agrees with the known generative process** (both
models rank `day_period`, `transfer_dependency`, and `precipitation_mm`
at or near the top — see `models/feature_importance/*.json`), which is a
useful sanity check that the models learned genuine structure rather than
noise, though this is a property of the synthetic data's construction,
not evidence of real-world validity.

These numbers are specific to this synthetic development dataset (seed
42) and this codebase's exact commit — see `models/run_metadata.json` for
the full reproducibility record (git SHA, DVC dataset hashes, config
hashes, dependency versions).

### Known limitations of the synthetic dataset specifically

- Reflects an authored generative model, not any real transit system —
  absolute metric values from it will not transfer to real deployments.
- No real GTFS calendar exceptions (holidays, service changes) — simplified
  weekday/weekend `service_id` only.
- Weather is a simulated latent process (diurnal/seasonal + autocorrelated
  storm episodes), not sourced from any real meteorological model.
- Synthetic zone grid substitutes for a real geography/weather-station map.
- `fares.csv` values are in `SYNTHETIC_UNITS`, not real currency — this
  table was added beyond the originally requested schema categories because
  the decision engine's cost term (`C`) needs a source; it maps to real
  GTFS `fare_attributes.txt`/`fare_rules.txt` when production data is
  connected.
- Mode representation is guaranteed (every configured mode appears at least
  once) rather than purely probabilistic, specifically so rail/ferry aren't
  silently absent at this dataset scale — see generation methodology.

### Known limitations of the feature pipeline specifically

- `historical_delay_minutes`, `rolling_7d_delay_minutes`, and
  `historical_reliability` are `NaN` for each route's first observed
  service_date (no prior history exists) — 3,240 of 388,800 rows on the
  current dataset. Left as `NaN` in `train/val/test.parquet` rather than
  silently filled; the persisted `preprocessor.joblib` (median-imputed,
  fit on train only) is what the training stage should use to handle them.
- The weather asof-join uses *observed* readings strictly before
  `scheduled_time`, not a forecast — a reasonable demo simplification, but
  production should join a forecast issued before T instead, since a
  same-window observation can still correlate with the very conditions
  causing a delay in ways a forecast wouldn't.
- `route_id`/`service_id`/`direction_id`/`route_type_gtfs` are joined into
  the interim table but not yet included in the default `ColumnTransformer`
  feature set (`src/preprocessing/pipeline.py`) — deferred to the training
  stage to decide whether route-identity features are worth the overfitting
  risk on an 18-route development network.

### Known limitations of Stage 4 training specifically

- The hyperparameter search is intentionally small (5 curated configs per
  model, no cross-validation — see rationale in `training/tune.py`), so it
  should be read as "a modest, reasonable search," not an exhaustive one;
  a wider search might find a better configuration.
- Random Forest training was markedly slower than expected — the
  deepest/largest configs (e.g. `max_depth: null`, 400 trees) took up to
  ~5 minutes each on 272K rows, ~9 minutes total for the 5-config search.
  XGBoost's `hist` tree method was consistently under 6 seconds per trial.
  This asymmetry itself is a real, measured result (see the Training time
  column in section 16), not a tuning artifact.
- No SHAP explainability was added — it's listed as optional in the Stage
  4 brief, and adding it means a new dependency not yet in
  `requirements.txt`; gain-based (XGBoost) and impurity-based (Random
  Forest) importance were used instead. Can be added later if wanted.
- Both models' ROC-AUC (~0.71) and PR-AUC (~0.52) indicate real but modest
  discriminative power — consistent with the intentional label noise in
  the synthetic data (see dataset limitations above), not a sign of a
  training bug. Do not expect these specific numbers to hold on different
  data.
- The decision threshold (0.5) was fixed by policy, not tuned — threshold
  sensitivity was computed on validation only (`evaluation.json`
  `diagnostics.*.val_threshold_sensitivity`) as a diagnostic, never used
  to pick a different threshold, and never computed on test.

### Known limitations of Stage 5 (MLflow tracking/registry) specifically

- **Neither candidate cleared the promotion gate** — F1 (~0.50–0.51) is
  below the configured `min_f1: 0.60`. This is the gate legitimately
  rejecting both models, not a bug; the thresholds were set as reasonable
  round numbers independent of what training happened to measure (see
  `params.yaml` `evaluation.promotion_gates`), specifically so they
  wouldn't be quietly adjusted to make something pass.
- **A genuine MLflow/XGBoost interop bug was found and fixed during this
  stage**: `mlflow.xgboost.load_model()` reconstructs an `XGBClassifier`
  that's missing the sklearn wrapper's `n_classes_` attribute, breaking
  `predict_proba`; separately, MLflow's generic pyfunc schema enforcement
  cannot round-trip pandas `category`-dtype columns through its JSON
  serving-input validation. `inference/model_loader.py` works around both
  by loading via each model's native flavor and patching `n_classes_` for
  XGBoost — verified to produce byte-identical predictions vs. the
  pre-registration model. A practical consequence: this XGBoost model
  cannot be served via MLflow's generic `mlflow models serve` /pyfunc
  REST path out of the box; it must be loaded in-process via the native
  flavor, exactly as `inference/model_loader.py` and the future FastAPI
  layer do.
- The Model Registry uses the local file-based tracking store (`./mlruns`)
  — confirmed to fully support registered models and aliases in this
  MLflow version, so no database backend was needed. This wouldn't
  necessarily hold for every future MLflow version; worth re-checking on
  upgrade.
- Lifecycle stages use **tags** (`lifecycle_stage`) + **aliases**
  (`production`), not MLflow's legacy `transition_model_version_stage`
  stage API — deprecated in this MLflow version (2.17.2), consistent
  with the Stage 5 brief's "match the installed MLflow version."
- The registry currently holds 4 versions of `RouteWise-Disruption-Model`
  (versions 1–2 from an initial run made before a round-trip validation
  bug was found and fixed, versions 3–4 from the corrected, validated
  run) — left in place rather than deleted, since they're real run
  history, not fabricated. Versions 3 (Random Forest) and 4 (XGBoost) are
  the ones with round-trip validation confirmed passing; see section 9.
- The reproducibility check (`training/reproducibility_check.py`)
  re-trains only the two models' *final chosen configurations*, not the
  full Stage 4 tuning grid — re-running the whole grid would be
  re-tuning, not a reproducibility check. Both came back with zero
  prediction difference across all 58,320 test rows and exact metric
  matches, on this machine/library-version combination; determinism is
  not a universal guarantee across all hardware/BLAS/thread-count
  configurations, only demonstrated on this one.

### Known limitations of Stage 6 (routing + decision engine) specifically

- The graph is a **static, representative-schedule** graph (one edge per
  route+direction leg), not a time-expanded graph — it does not model
  individual departures or how conditions might differ between the 8am
  and 6pm run of the same route. Disruption predictions are computed
  under one fixed **reference context** (`routing.prediction_context` —
  a documented datetime + weather assumption, not real-time), applied
  uniformly to every edge in the graph, not shifted per-leg along a route.
- Transfer penalties are applied at **path-aggregation time**, not baked
  into the Dijkstra/A* search weights — so candidate *generation* doesn't
  actively minimize transfers, only candidate *scoring* accounts for
  them. A path with many cheap-but-transfer-heavy legs could in principle
  be generated and then correctly scored worse, but a transfer-avoiding
  search strategy isn't implemented.
- No "walking" transport mode/layer exists — the Stage 2/3 dataset only
  has bus/tram/metro/rail/ferry. A transfer between two different modes
  at a shared stop is implicitly a walk-across-the-platform, but this
  isn't a separate, explicit graph element, since inventing walking data
  ungrounded in the dataset was avoided.
- A* has a genuine admissible heuristic only for the `time` objective;
  `cost`/`risk`/`combined` use heuristic=0 (admissible, but equivalent to
  Dijkstra with no speedup) — documented in `src/routing/path_search.py`
  rather than fabricating an unjustified heuristic.
- Edge `cost` is **apportioned**: a route's flat `fares.csv` fare divided
  equally across its legs — a documented derived estimate, not a
  per-leg fare that exists in the source data.
- The real generated graph has 11 of 70 stops fully isolated (never
  served by any route) and one edge with `travel_time == 0` (a
  minute-rounding artifact of very short legs) — both are genuine
  properties of the Stage 2 synthetic dataset, exercised directly by
  tests rather than hidden or special-cased away.
- `reroute()` is explicitly an "adaptive rerouting **capability**" per
  the Stage 6 brief — it recomputes recommendations given a caller-
  supplied probability update, but nothing in this stage connects it to
  a live/real-time data feed.

### Known limitations of Stage 7 (API) specifically

- **No authentication** — the Stage 7 brief explicitly says this isn't
  required yet ("unless the architecture needs it"), and it doesn't for
  a local/dev-only API. Documented here rather than silently absent:
  anyone who can reach the process can call every endpoint.
- `POST /reroute` requires the caller to already have an `edge_id` from a
  prior `POST /recommend-route` response (each segment now includes one
  — this was a real gap found and fixed while writing the API tests:
  segments didn't expose `edge_id` at all before). There's no separate
  "list edges near this stop" endpoint yet.
- `/reroute` recomputes the "before" route fresh from `origin`/
  `destination` (not from client-supplied route data) before applying the
  update, so `old_risk`/`old_score` always reflect the CURRENT graph
  state at request time, not necessarily whatever the client displayed
  earlier — the two could differ if the server's reference conditions
  changed between calls (they won't, in this stage, since nothing updates
  them automatically, but this is the honest behavior to document).
- The model and routing graph are loaded once per **process** at
  startup — running multiple API worker processes (e.g. `uvicorn
  --workers N`) would build N independent copies, not share one; no
  shared-cache/singleton-across-processes mechanism exists yet.
- CORS origins default to two common local dev ports
  (`localhost:3000`/`5173`) via `.env` — not meant as production values.
- Performance numbers in the "API Usage" section are in-process
  `TestClient` measurements on one dev machine, not a load test — no
  claim about concurrent-request throughput is made.

### Known limitations of Stage 8 (frontend) specifically

- Cost is shown as `N.NN units` (the real `SYNTHETIC_UNITS` from
  `fares.csv`), not a currency symbol — a deliberate deviation from the
  Stage 8 brief's own "₹40" example, since the backend has never dealt
  in real currency and displaying one would misrepresent synthetic data.
- Stop/route names are the synthetic generator's own labels ("Stop 40",
  route "R011") — there are no real place names in the Stage 2 dataset to
  show instead.
- Selecting one of the graph's 11 known-isolated stops (see Stage 6) as
  either endpoint correctly produces a "no route connects these two
  stops" error — this is the app behaving correctly against a real
  property of the synthetic network, not a frontend bug.
- `src/api/types.ts` is hand-mirrored against `api/schemas/*.py`, not
  generated — the two can drift if one side changes without the other;
  no codegen step exists yet.
- Accessibility was addressed directly (semantic landmarks, labeled
  form fields with `aria-invalid`/`aria-describedby`, `role="alert"`/
  `role="status"` live regions, visible `:focus-visible` states,
  `prefers-reduced-motion` support, keyboard-operable controls) and
  exercised via the real Playwright integration run, but no automated
  accessibility audit tool (e.g. axe-core) was run — that's a real gap,
  not a claim of a passed audit.
- No client-side routing library — the whole flow (search → results →
  details → reroute) lives in one page's local state, appropriate for
  the current single-screen scope.

### Known limitations of Stage 9 (monitoring) specifically

- "Current" data is a controlled batch from `data/processed/test.parquet`
  — this project has no live production traffic, so it stands in for a
  "new" batch. It is always labelled DEVELOPMENT/DEMO MONITORING and must
  never be read as live Chennai (or any real city's) transportation
  conditions.
- Because the default "current" batch is the very test split the model's
  recorded baseline metrics were measured on, the default (non-scenario)
  performance-monitoring run reproduces that baseline almost exactly by
  construction — it does not exercise genuine post-deployment performance
  drift. Real degradation detection is demonstrated separately via the
  seeded Scenario D controlled experiment (`src/monitoring/scenarios.py`,
  exercised in `tests/test_monitoring.py`).
- Real feature and prediction drift IS observed between the train
  (reference) and test (current) splits — driven by genuine seasonality
  in the synthetic weather generator and by the historical/rolling
  features' expanding time windows — not fabricated for demonstration
  purposes; see `data/interim/monitoring/latest_monitoring_report.json`.
- Operational metrics (`api/middleware.py`) are in-process counters for a
  single API instance — they reset on every restart and are not
  distributed/multi-instance production monitoring.
- The monitoring runner is a manual/scheduled offline process
  (`python -m src.monitoring.runner`), not triggered automatically by the
  API on a request or a schedule — no `dvc.yaml`/cron wiring exists yet
  (tracked as part of Stage 10's retraining-trigger work).
- Evidently HTML reports (`data/interim/monitoring/html_reports/`) are
  regenerated on every run and gitignored, per the brief's "do not commit
  large generated reports unnecessarily" — only the small machine-readable
  JSON report and reference-lineage metadata are committed.
